#### Step 1: Wire Packet Header Format & RFC 1071 Checksum Algorithm

##### Objective & Architectural Context
In catalogue P3, reliable UDP requires wire-level datagram framing, sequence numbering, acknowledgements, flags, and error detection. I designed a binary header packed in network byte order (Big-Endian) that fits within standard Ethernet MTU (1500 bytes) without IP fragmentation, while implementing the standard 16-bit One's Complement Internet Checksum (RFC 1071) from scratch without third-party libraries.

##### Prompt Given to AI
```text
I am designing a binary wire header for a custom Reliable UDP transport protocol (DART) in Python using standard `struct`. 
The packet must include:
- Magic identifier (2 bytes)
- Version (1 byte)
- Flags for DATA, ACK, SYN, FIN, RST (1 byte bitmask)
- 32-bit Sequence Number (4 bytes)
- 32-bit Acknowledgement Number (4 bytes)
- 16-bit Advertised Window (2 bytes)
- 16-bit Checksum (2 bytes)
- Variable payload (up to 1400 bytes MSS)

Can you show me the struct format string for big-endian packing and explain the RFC 1071 16-bit one's complement addition loop in Python, specifically how carry bit folding works if the payload has an odd byte length?
```

##### AI Response Summary
The AI provided the struct format string `!H B B I I H H` (16 bytes) and suggested an iterative loop over pairs of bytes, accumulating a 32-bit sum and folding carry bits:
```python
def internet_checksum(data):
    if len(data) % 2 != 0:
        data += b'\x00'
    total = sum((data[i] << 8) + data[i+1] for i in range(0, len(data), 2))
    while total >> 16:
        total = (total & 0xFFFF) + (total >> 16)
    return ~total & 0xFFFF
```

##### Critical Analysis & Core Logic Implemented by Areen
While the basic carry fold loop was mathematically correct, it was insufficient for an operational socket protocol:
- It lacked header checksum zeroing during serialization: the checksum field must be set to `0` prior to hashing over the header and payload, then stamped back in.
- It lacked payload length clamping against MSS, leaving socket buffers vulnerable to fragmentation.
- It did not provide socket-level validation or raise a custom protocol exception on corrupted packets.

**My Core Implementation (`dart/packet.py`):**
1. Implemented `compute_internet_checksum(data: bytes)` with explicit byte-order handling and odd-byte padding (`data + b'\x00'`).
2. Authored `DARTPacket.serialize()`: packed the header with `checksum = 0`, computed the checksum over the binary header concatenated with the payload, and inserted the calculated checksum into the final datagram.
3. Authored `DARTPacket.deserialize(data: bytes)`: enforced strict length checks (`HEADER_SIZE <= len(data) <= HEADER_SIZE + MAX_PAYLOAD_SIZE`), magic number verification (`0xDA87`), version matching, and checksum verification. Any corruption raises `PacketDecodeError("Checksum validation failed")`, causing the packet to be discarded cleanly at the socket boundary before reaching ARQ state.

```python
# Implemented by Areen in dart/packet.py
def compute_internet_checksum(data: bytes) -> int:
    if len(data) % 2 != 0:
        data = data + b'\x00'

    total_sum = 0
    for i in range(0, len(data), 2):
        word = (data[i] << 8) + data[i + 1]
        total_sum += word
        while total_sum > 0xFFFF:
            total_sum = (total_sum & 0xFFFF) + (total_sum >> 16)

    return (~total_sum) & 0xFFFF
```

##### Viva Defense Readiness
- **Examiner Question:** Why must carry bits be folded iteratively rather than just once?
- **Defense:** Adding 16-bit words into a 32-bit accumulator can produce multiple carries. When the carry `total >> 16` is added back to `total & 0xFFFF`, this addition itself can generate another carry (e.g. `0xFFFF + 1 = 0x10000`), necessitating a loop until all carries are resolved into the 16-bit field.
- **Live Demo Action:** I can introduce a bit-flip into the wire buffer live during the demo to show immediate checksum failure and drop.

#### Step 2: DART Adaptive Decision Engine & Finite State Machine

##### Objective & Architectural Context
The primary novel contribution of DART is replacing fixed transmission parameters with a dynamic, bounded, and explainable adaptive transmission engine. The engine observes channel feedback (measured RTT, timeout frequency, packet loss) and adjusts the transmission window and inter-packet pacing delay without causing oscillation.

##### Prompt Given to AI
```text
I am building the core adaptive decision engine for DART (Dynamic Adaptive Reliable Transport) in Python. 
I want to use an explainable Finite State Machine (STARTUP, STABLE, CONGESTION_DETECTED, RECOVERY) 
rather than an opaque reinforcement learning or complex heuristic.

Could you provide a Python dataclass structure representing engine configuration parameters 
(initial window, min/max bounds, decrease factor) and an Enum for the four states, 
along with suggestions on how to detect RTT inflation before actual loss occurs?
```

##### AI Response Summary
The AI provided basic `AdaptiveConfig` and `AdaptiveState` declarations and suggested comparing smoothed RTT ($SRTT$) to minimum recorded RTT ($min\_RTT$):
$$\text{Inflated if } SRTT > min\_RTT \times 1.35$$
However, the AI suggested adjusting the congestion window as a continuous floating-point number directly inside socket send loops.

##### Critical Analysis & Core Logic Implemented by Areen
The AI's suggestion was unusable for a discrete ARQ transport:
- Continuous floating-point window sizing breaks discrete packet window boundaries in Go-Back-N and Selective Repeat.
- An unconstrained adaptation engine causes "flapping" (rapid back-and-forth window contraction and expansion) under momentary jitter.
- The AI's code lacked an isolation contract: adaptation must be purely deterministic and decoupled from socket I/O so it can be evaluated against a static baseline under identical seeds.

**My Core Implementation (`dart/adaptive/engine.py` & `dart_transport/adaptive.py`):**
1. **Designed the Deterministic FSM:**
   - **`STARTUP`:** Bounded ramp-up (+1 packet per round-trip) until reaching an initial stable window of 8.
   - **`STABLE`:** Conservative Additive Increase (AIMD): increases transmission window by 1 only after 2 consecutive healthy RTT intervals without loss or inflation, while reducing pacing delay.
   - **`CONGESTION_DETECTED`:** Multiplicative Decrease: on any packet loss or timeout event, window is immediately reduced by `decrease_factor` ($0.5\times$ or $0.7\times$), clamped to `min_window = 1`, and a protective pacing delay (+2.0 ms) is injected to drain bottleneck router queues.
   - **`RECOVERY`:** Freezes window scaling and holds steady until `recovery_healthy_required = 3` consecutive clean observations are logged, preventing catastrophic multi-reduction on a single burst loss.
2. **RTT Smoothing & Early Queue Detection:** Implemented standard EWMA smoothing ($SRTT = 0.875 \cdot SRTT + 0.125 \cdot RTT_{sample}$) and checked against $min\_RTT \times 1.35$. If latency inflates without loss, pacing is throttled before drops occur.
3. **Pluggable Base Architecture:** Created `BaseAdaptiveEngine` and `FixedBaselineEngine` to ensure experimental fairness—both static P3 and adaptive DART share the identical socket and ARQ codebase.

```python
# Implemented by Areen in dart/adaptive/engine.py
class DARTAdaptiveEngine(BaseAdaptiveEngine):
    def on_rtt_sample(self, rtt: float) -> None:
        self.rtt_history.append(rtt)
        if len(self.rtt_history) > 50:
            self.rtt_history.pop(0)

        if self.min_rtt is None or rtt < self.min_rtt:
            self.min_rtt = rtt

        if self.srtt is None:
            self.srtt = rtt
        else:
            self.srtt = 0.875 * self.srtt + 0.125 * rtt

        # Delay-based early congestion warning (bufferbloat mitigation)
        if self.min_rtt and self.srtt > self.min_rtt * self.config.rtt_inflation_threshold:
            self.pacing_ms = min(self.config.max_pacing_ms, self.pacing_ms + 1.0)
            return

        if self.state == AdaptiveState.STABLE:
            self.healthy_observations += 1
            if self.healthy_observations >= 2:
                self.window = min(self.config.max_window, self.window + self.config.window_increase_step)
                self.pacing_ms = max(0.0, self.pacing_ms - 0.5)
                self.healthy_observations = 0
```

##### Viva Defense Readiness
- **Examiner Question:** Why is AIMD preferred over Multiplicative Increase Multiplicative Decrease (MIMD)?
- **Defense:** MIMD does not converge to fairness when competing for bandwidth and leads to wild oscillations. AIMD guarantees asymptotic stability and convergence to an optimal operating point.
- **Live Demo Action:** I can alter `decrease_factor` live from `0.5` to `0.8` or adjust `rtt_inflation_threshold` to demonstrate immediate adaptation changes during a live file transfer.
